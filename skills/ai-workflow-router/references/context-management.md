# Context Management

只在長任務、上下文壓力不低，或使用者明確詢問 token／context 管理時載入本文件。

## 核心原則

- Context window 是容量上限，不是品質保證；優先提高訊號密度，而不是填滿可用空間。
- 沒有跨模型通用的降智臨界值。門檻是操作警戒線，應同時看使用率、任務階段與行為訊號。
- 為後續推理、工具結果及最終輸出保留空間；不要等到硬上限才整理。
- 主 context 只保留目標、約束、已確認決策、目前狀態、驗證證據、風險與下一步。
- 原始搜尋結果、完整 logs、過期方案、重複規格與大段 diff 應留在檔案或工具來源，需要時再讀。

## 操作警戒線

只在 agent 能可靠取得使用率時採用百分比；否則填 `N/A`，使用下一節的壓力訊號。

| 使用率 | 壓力 | 建議行為 |
| --- | --- | --- |
| 0–35% | `low` | 正常處理；維持 focused reads 與最小工具輸出 |
| 35–55% | `medium` | 停止重複貼全文；改用路徑、摘要、just-in-time retrieval |
| 55–70% | `high` | 建立 checkpoint；清理舊工具輸出，必要時 compact |
| 70–80% | `critical` | 不開始新階段；優先子代理、handoff-reset 或新 context |
| 80% 以上 | `critical` | 暫停複雜實作／review；先完成可驗證 handoff，再 reset／compact |

## 提前觸發的壓力訊號

即使使用率較低，出現任一訊號也至少提升一級處理：

- 重複讀取或詢問已確認資訊。
- 忘記明確約束，或重新提出已否決方案。
- 新舊決策混用、前後說法矛盾。
- 修改與搜尋範圍持續擴張。
- 用模糊摘要代替檔案、測試或錯誤訊息等證據。
- 同一 context 同時承擔大範圍探索、實作與自我 review。

## 降載順序

使用能解決問題的最輕手段，依序升級：

1. 限縮搜尋、檔案與工具輸出，只讀目前步驟所需內容。
2. 清除或停止重送已消化的原始結果，以路徑及結論取代。
3. 建立結構化 checkpoint，把 durable state 寫到 artifact。
4. 同一任務需要連續性時 compact。
5. 將可隔離、高噪音的探索或 research 放入乾淨子代理。
6. 階段已切換或壓力仍高時 handoff-reset；review 使用 fresh context。

## 子代理路由

適合委派：

- 大範圍唯讀探索或獨立 research。
- 預期產生大量搜尋、文件或工具輸出的工作。
- 不修改相同檔案、沒有前置相依的切片。
- 需要與實作者隔離偏見的 review。

不適合委派：

- 單一小修改，委派成本高於執行成本。
- 共享 mutable state 或必須嚴格循序完成。
- 需要使用者做產品、風險或範圍決策。
- 無法定義檔案邊界與驗收條件。

## Artifact-first 交接契約

完整探索結果優先寫入檔案、測試、diff 或其他持久 artifact；回到主 agent 的訊息只保留：

```text
目標：<這個子任務要回答什麼>
結論：<已確認結果>
證據：<檔案路徑、行號、測試或 artifact>
決策：<已採用與已否決方案>
變更：<實際修改；唯讀任務填「無」>
驗證：<命令與結果>
風險：<未驗證或仍可能失敗之處>
下一步：<主 agent 可直接執行的動作>
```

不要把完整工具歷史、所有候選方案或整份檔案複製回主 context。交接資訊不足時，補齊缺欄，不以大量原始輸出代替結論。
